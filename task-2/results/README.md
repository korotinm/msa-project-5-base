# Задание 2. Дизайн модуля пакетной обработки данных

## Контекст

Каждое утро в 06:00 нужно выгрузить кастомные CSV-прайс-листы для B2B-клиентов. Источник: PostgreSQL
(`products` 5–10 тыс. строк, `categories` 50–200, `clients` 100–500, `client_prices` 10–20 тыс.).
Логики обработки нет: соединить четыре таблицы и записать результат в файл. Инфраструктура магазина — микросервисы в облаке.

Объём небольшой: весь набор помещается в память одного процесса, выгрузка занимает секунды.

## Сравнение решений

| Критерий | Spring Batch | Apache Airflow | K8s CronJob | Spark |
|---|---|---|---|---|
| Наличие cron-расписания | Нет своего планировщика, нужен `@Scheduled`/Quartz или внешний триггер | Да, `schedule` в DAG | Да, поле `schedule` в манифесте | Нет, нужен внешний планировщик (Airflow, k8s) |
| Сложность реализации логики обработки | Средняя: Reader/Processor/Writer, много конфигурации для JOIN + CSV | Низкая: пара операторов или Python-функция | Низкая: один скрипт с SQL и записью в CSV | Средняя: сессия, DataFrame, коннекторы, для JOIN четырёх небольших таблиц избыточно |
| Ресурсоёмкость | Средняя: JVM + Spring-контекст, но запускается и завершается | Высокая: постоянно работают webserver, scheduler, БД метаданных, воркеры | Минимальная: под живёт секунды и освобождает ресурсы | Высокая: driver + executors, JVM, старт кластера |
| Масштабируемость и сложность реализации | Партиционирование и параллельные шаги есть, но требуют настройки | Масштабируется воркерами, но для 10 тыс. строк не нужно | Горизонтально: Job на клиента или группу клиентов, `parallelism`; для текущего объёма не требуется | Отлично масштабируется, но объём в 5–10 тыс. строк этого не требует |
| Развёртывание в облаке и интеграция с микросервисами | Отдельный Java-сервис, нужен образ и деплой | Нужен свой кластер Airflow (или Cloud Composer / MWAA) и его поддержка | Нативно: инфраструктура уже в k8s, нужен только образ и манифест | Spark-кластер или Operator, сложная настройка |
| Интеграция с логированием и мониторингом | Micrometer, Actuator, хорошо | Встроенные UI и метрики, email/Slack | stdout-логи подхватываются сборщиком, статус Job через kube-state-metrics в Prometheus | Spark UI, метрики через sink, отдельная настройка |

## Вывод

Выбираем **K8s CronJob**.

- Задача укладывается в «один запрос и файл»: нет ветвлений, зависимостей между шагами и больших данных, поэтому оркестратор (Airflow) и вычислительный движок (Spark) здесь избыточны.
- Spring Batch ничего не добавляет для этой задачи: у него нет собственного планировщика, при этом требуется отдельный Java-сервис со своей конфигурацией.
- Магазин уже работает на микросервисах в облаке, то есть в k8s: CronJob не добавляет в инфраструктуру ничего нового, нужны только образ и манифест.
- Ресурсы потребляются только на время запуска.

Если задачи усложнятся (ветвления, зависимости между выгрузками, десятки пайплайнов), стоит перейти на Airflow:
скрипт из контейнера переносится в `KubernetesPodOperator` без переписывания.

## To Be

Диаграммы: [C4_Context.puml](C4_Context.puml), [C4_Container.puml](C4_Container.puml).

Как работает решение:

1. В 06:00 CronJob создаёт Job, `concurrencyPolicy: Forbid` не позволяет запуститься второму экземпляру, пока не завершился первый.
2. Под поднимает контейнер с Python-скриптом, параметры подключения берёт из Secret/ConfigMap.
3. Скрипт одним запросом читает данные из PostgreSQL (лучше с реплики для чтения, чтобы не нагружать боевую БД): соединяет `client_prices`, `clients`, `products`, `categories`.
4. Строки группируются по клиенту, для каждого формируется свой CSV.
5. Файлы загружаются в объектное хранилище (S3/GCS), оттуда их забирают менеджеры и интеграции.
6. Под завершается; статус Job, метрики и логи уходят в Prometheus и ELK; при ошибке срабатывает retry (`backoffLimit`) и алерт.

## План внедрения

1. Согласовать формат прайс-листа: колонки, кодировка, разделитель, имя файла (`price_<client>_<date>.csv`). Если нужен XLS, добавить библиотеку записи.
2. Подготовить SQL: JOIN `client_prices` → `clients`, `products` → `categories`, индексы по `client_id` и `product_id`, проверка плана запроса.
3. Создать пользователя БД только для чтения, настроить доступ к реплике.
4. Написать скрипт выгрузки (psycopg2 + csv), проверить на копии данных, добавить логи и коды возврата.
5. Собрать Docker-образ, опубликовать в реестр.
6. Подготовить манифесты: CronJob (`schedule: "0 6 * * *"`, `concurrencyPolicy: Forbid`, `backoffLimit: 3`, `ttlSecondsAfterFinished`, requests/limits), Secret и ConfigMap.
7. Настроить доставку: bucket, права на запись для сервисного аккаунта, политика хранения файлов.
8. Мониторинг: метрики `kube_job_status_failed`, время последнего успешного запуска, число и размер файлов, алерт при отсутствии успешного запуска к 06:30.
9. Прогнать на стенде (minikube или тестовый namespace), сверить результат с эталонной выгрузкой, затем включить в проде.
10. Описать runbook: как перезапустить выгрузку вручную (`kubectl create job --from=cronjob/price-export`).
